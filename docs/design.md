# Design notes

## Goal

Hear a local source (computer, TV, turntable preamp) on the speakers connected to the CAST PRO-1's optical output with
low delay, starting by itself when sound arrives, while Music Assistant playback and Home Assistant announcements to the
same speakers keep working.

## Hardware facts used

- The line-in ADC (PCM1808) and the analog-output DAC (PCM5122) share one I2S port: they cannot run together. So
  passthrough is optical-only, and only while Audio Output is set to Optical.
- The optical S/PDIF signal is generated by the ESP32-S3 in software, from the same mixer that plays Music Assistant and
  announcements. A third mixer input is therefore the natural place for line-in.
- The ESP32-S3 has limited internal RAM; the S/PDIF output, the ADC and announcements each need DMA-capable internal
  buffers. This is the main risk of the design (see `packages/memory-saver.yaml`).
- Apollo's stock firmware has no OTA password; the device has two app slots of about 3.84 MB (the stock image is about 2.25 MB).

## Architecture: a third mixer input

- Apollo's configuration is consumed as a remote package pinned to a commit. This repository only adds to it, using
  ESPHome's `!extend` / `!remove` to override by id. No Apollo file is copied.
- A new mixer source speaker `linein_mixer_input` sits next to Apollo's media and announcement inputs. The mixer sums them.
- A data callback on the ADC (Apollo's `line_in_adc`; several consumers are allowed) does two things for every block of
  samples: it measures the level in 100 ms windows, and, while the controller wants the path open, applies the gain and
  writes the samples into the mixer input without ever blocking the microphone task.
- A 50 ms controller decides ADC ownership, signal debounce with hysteresis, keep-warm, who plays, ducking and the
  entities.
- Priority is done with ducking: "Line In wins" turns the Music Assistant input down by 80 dB; "Duck other" by the
  configured amount; "Mix" and "Music Assistant wins" do not duck (the latter closes the line-in path while Music
  Assistant plays).

### Rejected: writing straight to the S/PDIF speaker

About 25-75 ms less latency, but two writers on one buffer, and it would break Music Assistant's sync. Fragile.

## Decisions worth knowing about

**Keep warm.** After silence the S/PDIF output stops, and takes 1-2 s to start again, cutting the start of the next
sound. Shorter *Start After* did not help. Holding the path open (playing silent line-in) for 15 minutes after the last
signal avoids the restart. It costs a continuously running output during that time; some receivers may then not enter
standby, which I have not checked.

**Single owner of ducking.** Apollo's media-player hooks duck and un-duck the media input at announcement start/end, and
un-duck it on every state publish (including volume changes). With line-in also ducking that input, the two fight, and
the music came back for about a second. The fix is structural, not a timer: one script (`lp_duck_sync`) is the only code
that calls `apply_ducking`; Apollo's hooks and the controller call it; it only sends a ramp when the target changes.

**Release After pauses during announcements.** An announcement ducks line-in, and the source can sit at its noise floor
around it. If that silence counted, *Release After* could run out during the announcement and un-duck the music for a
moment. The silence timer restarts with the first quiet window after the announcement. A side effect: the signal can
only drop *Release After* seconds after an announcement ends, at the earliest.

**Self-update removal stays in the main file.** It is needed by every build, not only some. Apollo's own files still
call `check_for_update` and `apply_ota_source` by id, so those are kept as no-ops rather than removed.

**Memory-saver is optional and overrides by id.** It switches `espnow` and `esp32_ble` off at boot and neutralises the
runtime paths that would turn them back on. It must come after the main file in the package list and needs Apollo's ids
to exist.

## Out of scope

- Passthrough to the analog output (would need ESPHome `full_duplex` I2S and about 38 KB more internal RAM, estimated).
- A bit-perfect digital path (the CAST PRO-1 has no optical input).
- Latency below about 100 ms (would need patching the S/PDIF buffer count through an external component).

## ESPHome mechanics (verified)

- Remote package, long form (`url`, `ref`, `files:` list) and local `!include` both work for the main file and the two
  add-ons; see README and `example-device.yaml`.
- Replacing keys that a package defines is a two-step `!extend` (first entry `!remove`s the keys, second adds the new
  ones). Removing a script and defining it again under the same id in the same file works the same way.
